  - 컨테이너 이미지에는 코드만 포함하고, 실행 시 필요한 환경설정 값(키밸류)는 ConFigMap으로 관리
    - ConfigMap = 설정 데이터를 Kubernetes 리소스로 보관
    - Volume = 그 ConfigMap을 Pod가 사용할 수 있게 연결
    - VolumeMount = 컨테이너 내부 어느 경로에 보이게 할지 결정
    - Volume은 Pod에 속하고, VolumeMount는 각 Container에 속
  - ConfigMap에 application-prod.yaml을 저장하고 → 그것을 Volume으로 만들고 → /app/config에 VolumeMount해서 → 컨테이너의 Spring Boot가 외부 설정 파일로 사용하게 만든 구조다.
  - ConfigMap 자체는 Kubernetes 리소스라 etcd에 저장되고, Volume은 그 ConfigMap 데이터를 Pod 안으로 가져와 쓸 수 있게 연결하는 방식
  - sk117-myfirst-configmap에 application-prod.yaml을 저장 → config-volume으로 연결 → Pod의 /app/config에 마운트 → Spring Boot가 prod 설정으로 읽는다.
  - prod 파일 전체를 ConfigMap의 하나의 key-value로 저장 → 그 ConfigMap을 Volume으로 연결 → 컨테이너에 파일 형태로 Mount → Spring Boot가 그 설정 파일을 읽어서 설정을 적용

# 궁금한점

- 쿠버네티스의 네임스페이스와 컨테이너 네임스페이스

Kubernetes Namespace = 리소스를 관리하기 위한 논리적 구역, 쿠버네티스 안에서 리소스를 논리적으로 분류하는 관리 구역
Linux/Container Namespace = 프로세스의 실행환경을 실제로 격리하는 커널 기능, 진짜 Linux 커널이 프로세스의 실행환경을 격리하는 기술

그리고 같은 Pod 안의 컨테이너들은 Kubernetes가 의도적으로 같은 Network Namespace를 공유해서 서로 localhost 통신 가능하게 함

- config 말고 pvc써야할때

“앱에게 알려줄 값” → ConfigMap
“앱이 사용하면서 만들어내고 계속 보존해야 할 데이터” → PVC
PVC라면 일반 파일시스템처럼 평범한 파일 I/O를 사용할 수 있음
반면 ConfigMap은 파일시스템처럼 쓰는 저장공간이 아님. ConfigMap을 Volume으로 마운트하면 컨테이너에서는 파일처럼 보이지만, 그건 Kubernetes가 ConfigMap 데이터를 파일 형태로 보여주는 것에 가깝다.
즉 설정을 바꾸고 싶으면 ConfigMap 리소스 자체를 바꿔야 함

PVC는 앱이 직접 /data로 이동해 앱이 직접 create, write, update, delete 가능

ConfigMap = Kubernetes가 관리하는 “설정 묶음”을 파일처럼 보여줌
PVC = 애플리케이션이 실제로 읽고 쓰는 “디스크/파일시스템”

| 데이터                  | 자연스러운 선택    | 이유                         |
| ----------------------- | ------------------ | ---------------------------- |
| `application-prod.yaml` | ConfigMap          | 사람이 정하고 앱이 읽는 설정 |
| DB 접속 주소            | ConfigMap/Secret   | 설정값                       |
| 사용자 업로드 이미지    | PVC/Object Storage | 실행 중 계속 생성·삭제       |
| DB 데이터 파일          | PVC                | Pod가 죽어도 유지            |
| 여러 Pod가 공유할 파일  | PVC(EFS 등)        | 공통 파일시스템 필요         |
| 비밀번호/API Key        | Secret             | 민감한 설정                  |
