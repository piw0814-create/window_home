# 궁금한점

- 하이퍼 파라미터 조절 방향 및 팁?

### 1. Random Forest

```python
RandomForestClassifier(
    n_estimators=100,
    max_depth=8
)
```

| 파라미터            | 증가시키면                 | 일반적인 방향                               |
| ------------------- | -------------------------- | ------------------------------------------- |
| `n_estimators`      | Tree 수 증가               | 예측 안정성 ↑, Test 성능 약간 ↑ 후 포화     |
| `max_depth`         | Tree 깊어짐                | Train 정확도 ↑, 너무 크면 과적합 ↑          |
| `min_samples_leaf`  | Leaf 최소 데이터 증가      | 모델 단순화, 과적합 ↓                       |
| `min_samples_split` | 분할 조건 엄격             | 모델 단순화, 과적합 ↓                       |
| `max_features`      | 노드에서 보는 Feature 증가 | 개별 Tree 강해짐, Tree끼리 유사해질 수 있음 |

특히 `n_estimators`는 좀 특이해.

```text
100 → 300 → 500
```

으로 늘려도 Random Forest는 보통 **갑자기 과적합되지는 않아.** 여러 Tree의 평균을 내기 때문이야.

대신:

```text
정확도
 ↑
 |        ─────────
 |      /
 |    /
 |___/______________→ 트리 수
    100 300 500
```

어느 순간부터 성능이 거의 안 오르고 계산량만 증가함.

반면 `max_depth`는:

```text
max_depth ↑
→ Tree 하나하나가 세밀해짐
→ Train 정확도 ↑
→ 너무 깊으면 Test 정확도 ↓
```

그래서:

```text
Train 0.85 / Test 0.82
→ depth 조금 늘려볼 수 있음

Train 0.99 / Test 0.80
→ depth 줄이는 방향
```

### 2. XGBoost

여기는 `n_estimators`와 `learning_rate`를 **묶어서 보는 게 핵심**이야.

```python
XGBClassifier(
    n_estimators=1000,
    max_depth=5,
    learning_rate=0.1
)
```

Boosting은:

```text
Tree 1
 ↓
틀린 부분 보완하는 Tree 2
 ↓
또 보완하는 Tree 3
 ↓
...
```

이기 때문에 Tree 수가 너무 많으면 계속 학습하면서 **과적합 가능성**이 커져.

#### `n_estimators`

```text
증가
→ 더 많이 보정
→ Train 정확도 ↑
→ 적당히는 Test 정확도 ↑
→ 너무 많으면 Test 정확도 ↓ 가능
```

#### `max_depth`

```text
증가
→ Tree 하나가 더 복잡
→ Train 정확도 ↑
→ 과적합 위험 ↑
```

XGBoost에서는 보통 Random Forest보다 **얕은 Tree를 많이 사용하는 방식**이 잘 맞아.

예를 들어:

```python
max_depth=3~6
```

정도로 많이 시작해.

#### `learning_rate`

이게 매우 중요해.

```python
learning_rate = 0.1
```

이면 새 Tree가 배운 것을 10% 정도씩 반영한다고 생각하면 돼.

```text
learning_rate ↑
→ Tree 하나의 영향력 ↑
→ 빠르게 학습
→ 적은 Tree로도 성능
→ 너무 크면 과적합/불안정

learning_rate ↓
→ 조금씩 천천히 학습
→ 일반화가 좋아질 가능성
→ 더 많은 Tree 필요
```

그래서 둘은 이렇게 연결돼.

```text
learning_rate ↓
      +
n_estimators ↑
```

가 자주 같이 움직임.

예:

```python
# 빠르게
learning_rate=0.1
n_estimators=300

# 천천히 세밀하게
learning_rate=0.03
n_estimators=1000
```

흔히 후자가 더 좋은 성능을 낼 가능성이 있지만 계산량이 커져.

### 3. LightGBM

```python
LGBMClassifier(
    n_estimators=100,
    max_depth=5,
    learning_rate=0.1
)
```

기본 방향은 XGBoost와 거의 같아.

```text
n_estimators ↑
→ 학습량 ↑
→ 너무 많으면 과적합

max_depth ↑
→ 복잡도 ↑
→ 과적합 ↑

learning_rate ↓
→ 천천히 학습
→ n_estimators를 같이 늘림
```

그런데 LightGBM에서는 `max_depth`만큼 중요한 게 하나 더 있어.

```python
num_leaves
```

LightGBM은 **leaf-wise**로 가장 이득이 큰 Leaf를 계속 쪼개기 때문에 Tree가 공격적으로 복잡해질 수 있어.

```text
num_leaves ↑
→ 표현력 ↑
→ Train 정확도 ↑
→ 과적합 위험 ↑
```

그래서 LightGBM에서 과적합이면:

```python
max_depth ↓
num_leaves ↓
min_child_samples ↑
```

같이 볼 수 있어.

## 비교

```text
            적당한 복잡도
                 ↓
Test Acc       /\
              /  \
             /    \
____________/      \________
     과소적합        과적합
```

이 가운데를 찾는 작업이 하이퍼파라미터 튜닝이야.

> **깊이/Leaf 수 ↑ = 모델 복잡도 ↑ → Train 정확도는 대체로 ↑, 과적합 위험 ↑**
> **Learning rate ↓ = 천천히 보정 → 대신 Tree 수를 ↑**
> **Tree 수 ↑ = RF는 안정화, Boosting은 학습량 자체가 증가하므로 과적합 가능성도 봐야 함.**

특히 네가 지금 세 모델을 비교 중이면 `Train 정확도 / Test 정확도`를 같이 찍어가면서 이 방향으로 조절하면 하이퍼파라미터가 왜 바뀌는지 감이 금방 잡혀.

- 스케일링 필요성
  - 거리·계수·Gradient에 민감 → Scaling
  - Tree의 임계값 분할 → Scaling 불필
