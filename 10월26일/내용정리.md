**“먼저 간단히 처리할 수 있는지 보고, 필요하면 문서를 찾아 설명하고, 확인한 뒤 내보내는 구조”**

- 먼저 문서는 미리 등록 → 승인 → 내용 추출·분할 → 임베딩·색인 → 배포해 둬. 질문이 올 때마다 PDF 전체를 처음부터 읽는 건 아니야.

- 질문이 들어오면 다음 순서로 움직여.

1. 누가 묻는지 확인한다.
   Java가 로그인·역할을 확인하고, 그 사람이 볼 수 있는 문서와 적용 판본을 정해 RAG에 전달해. RAG도 인증을 다시 확인해.
   → 예비 점주에게 운영 점주 전용 레시피가 노출되면 안 되니까.
2. 단순한 화면 안내인지 확인한다.
   “가맹 준비 자료를 모아줘”는 문서 보관함으로 안내해.
   → 자료 목록 요청을 엉뚱한 법령 상담으로 바꾸지 않으려는 거야. 이때는 AI를 호출하지 않아.
3. 레시피를 바로 조회할 수 있는지 확인한다.
   “아이스 바닐라라테 시럽 몇 펌프?”는 저장된 JSON에서 값을 가져와. 문서의 판본·원문과도 맞는지 확인해. 온도가 필요하면 핫·아이스를 물어봐.
   → 정해진 계량·순서를 AI가 다시 만들어낼 이유가 없으니까.
4. 상담이 필요하면 질문의 대상을 정리한다.
   독립적인 질문은 그대로 검색하고, “그 돈에 교육비도 포함이야?”처럼 생략된 대상이 있을 때만 앞 대화를 참고해.
   → 과거 대화를 무조건 섞으면 현재 질문의 주제가 바뀔 수 있어. 이전 AI 답변은 사실 근거로 사용하지 않아.
5. 허용된 문서에서 근거를 찾는다.
   의미가 비슷한 내용을 찾는 벡터 검색과, 정확한 용어를 찾는 키워드 검색을 함께 사용해.
   → “돌려받다”와 “반환” 같은 표현 차이도 잡고, “교육비·보증금” 같은 항목명도 놓치지 않으려는 거야.
6. 답변에 필요한 부분을 골라 문맥을 붙인다.
   필요한 경우 AI가 검색 결과의 순서를 다시 정하고, 코드가 같은 조항·표의 주변 설명을 함께 가져와.
   → 숫자만 가져오고 단위나 예외를 빠뜨리는 일을 줄이기 위해서야.
7. AI가 설명하고, 코드가 값과 출처를 연결한다.
   AI는 질문에 필요한 결론·조건을 문장으로 작성해. 표의 숫자는 코드가 원래 셀에서 복원하고, 문장에 연결한 출처와 수치를 검사해.
   → 설명은 유연하게 하되, 금액이나 계량을 임의로 만들지 못하게 하는 거야.
8. 정말 질문에 맞는 답인지 확인한다.
   코드는 숫자·단위·인용 연결을 확인하고, AI 검수는 대상·조건·예외와 질문 누락을 확인해.
   → 원문에 숫자가 있다고 해서 그게 질문한 항목의 숫자라는 뜻은 아니니까.
9. 문제가 있으면 제한적으로 보완한다.
   설명이 틀리면 다시 쓰고, 근거가 부족하면 추가 검색이나 관련 본문 조회를 해. 보완은 기본적으로 한 번으로 제한해.
   → 끝없이 검색·재작성을 반복하며 시간과 비용이 늘어나는 걸 막으려는 거야.
10. 최종 답변과 상태를 코드로 조립한다.
    확인된 답변에는 출처·판본을 붙여 내보내고, 확인하지 못한 부분은 보류하거나 담당자 확인을 안내해. 시스템 오류는 근거 부족과 구분해.
    → 사용자가 무엇을 근거로 답했는지, 어디까지 믿고 확인해야 하는지 알 수 있어야 하니까.
    역할만 기억하면 쉬워. AI는 질문과 문서의 의미를 해석하고, 코드는 권한·저장값·출처 연결·실행 한계를 통제해. 검수도 완벽하진 않아서, 실제 질문으로 품질을 따로 확인하는 거고.

- 우리가 어떤 레그 기술들을 사용했는지 그 이유와 함께 설명

- 우리 시스템은 검색을 정교하게 만든 Advanced RAG에, 필요한 경우만 추가 조회하는 제한적인 Agentic RAG를 결합한 구조야. 레시피는 별도로 빠른 조회 경로를 사용해.
- 사용한 기술 우리 시스템에서 하는 일 사용한 이유
- 문서 구조 기반 청킹 법령은 조문 중심으로, 일반 문서는 쪽·본문·표 단위로 나눔 일정 글자 수로만 자르면 조문의 조건이나 표의 항목·수치가 떨어질 수 있어서
- 청크 메타데이터 문서 ID·판본·페이지·적용 기간·공개 범위를 청크와 함께 저장 답변 출처를 표시하고, 사용자에게 허용된 시점·문서만 검색하기 위해
- 구조화 표 데이터 원문과 대조한 표의 제목·행·열·단위·값을 검색 근거로 활용 PDF에서 표를 텍스트로만 읽으면 어떤 금액이 어떤 항목인지 흐트러지기 쉬워서
- OpenAI 임베딩 문서와 질문을 의미를 나타내는 벡터로 변환 질문과 문서의 표현이 달라도 비슷한 의미를 찾기 위해
- FAISS 벡터 검색 질문 벡터와 가까운 문서 조각을 찾음 현재 문서 규모에서 별도 벡터 DB 서버 없이 간단하게 운영할 수 있어서
- BM25 키워드 검색 정확한 용어가 들어 있는 문서를 찾음. 한국어 분석에 Kiwi 사용 ‘이행보증금’, 법령 용어처럼 정확한 단어가 중요한 질문을 의미 검색만으로 놓치지 않도록
- Hybrid Search + RRF 벡터 검색과 키워드 검색의 순위를 합침 의미와 정확한 용어를 함께 반영하고, 서로 다른 검색 점수를 직접 더하는 문제를 피하기 위해
- LLM 재순위화 검색 후보 중 질문에 더 적합한 근거를 다시 선택 비슷한 문서가 검색돼도 실제 질문의 대상·조건과 맞는 자료를 우선하기 위해
  문맥 확장·섹션 조회 선택한 청크 주변의 같은 섹션이나 관련 부분을 추가로 읽음 표의 숫자만 가져오고 단위·예외·반환 조건을 놓치는 일을 줄이기 위해
- 선택적 질문 재작성 필요한 경우 이전 대화의 ‘그거’, ‘언제까지’ 등을 구체적인 검색 질문으로 바꿈 후속 질문은 짧아도 앞선 대화의 대상이 이어지기 때문
- LangGraph 기반 흐름 제어 준비 → 검색 → 생성 → 검수, 필요하면 추가 조회·수정으로 연결 검색 한 번으로 부족한 질문을 보완하면서 호출 횟수와 종료 조건을 코드로 제한하기 위해
- 구조화 출력·근거 검증 AI가 답변 항목과 인용 정보를 정해진 형식으로 작성하고, 코드와 AI가 나눠 검증 문장이 자연스럽다는 이유만으로 잘못된 수치나 관련 없는 출처를 통과시키지 않기 위해

- 각 기술이 실제로 이어지는 순서는 이렇게 보면 돼.

               질문·대화 맥락 확인
               ↓
               권한·판본·적용 시점에 맞는 문서로 검색 범위 제한
               ↓
               벡터 검색 + BM25 → RRF로 결합
               ↓
               필요하면 재순위화·주변 문맥 확장
               ↓
               근거를 바탕으로 답변 작성
               ↓
               수치·인용은 코드로, 의미·적용 조건은 AI로 검수
               ↓
               부족하면 제한적으로 추가 조회·수정
               ↓
               답변 + 출처 또는 확인하지 못한 부분 반환
               여기서 중요한 건 AI와 코드의 역할을 나눈 것이야.

- AI: 질문 의도 이해, 관련 근거 선택, 설명 작성, 근거와 설명의 의미 일치 판단.
- 코드: 접근 권한, 판본·시점 필터, 표의 실제 값 복원, 인용 ID와 수치 연결 확인, 호출·반복 상한 관리.
  레시피 질문은 이 전체 과정을 매번 거치지 않아. 지원하는 질문이라면 원문과 연결된 구조화 레시피에서 계량·순서를 코드로 반환해. 빠르고 정확한 값 확인이 목적이기 때문이야. HOT·ICED에 따라 값이 다르면 먼저 온도를 확인하고.

- 기술 이름도 정확하게 구분하면 좋아.

- Advanced RAG 적용: 구조 기반 청킹, 메타데이터 필터, 하이브리드 검색, 재순위화, 문맥 확장
- Agentic RAG 제한적으로 적용: 필요할 때 도구로 추가 조회하고 결과를 보완
- Self-RAG·Corrective RAG 근거 검수·재작업이라는 유사한 패턴을 사용하며, 해당 연구 방식을 그대로 구현한 것은 아님
- Parent–Child 작은 검색 결과에서 상위·주변 문맥을 확장하는 유사 전략 사용
- Qdrant·HNSW 미사용. 현재 FAISS의 정확 검색 사용
- Cross-Encoder Reranker 미사용. 현재는 LLM으로 후보를 재선택
- Graph RAG 미사용. LangGraph는 처리 흐름을 관리하는 도구이며 지식 그래프 검색과는 별개
- RAGAS 현재 실행 경로의 필수 구성 요소로 사용하지 않음

- 우리 목적에 맞춰 표현하면, **“의미와 키워드로 근거를 찾고, 코드와 AI가 역할을 나눠 검수하며, 부족할 때만 제한적으로 추가 검색하는 상담 RAG”**라고 설명할 수 있어.
