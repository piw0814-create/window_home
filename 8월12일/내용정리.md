- 컴포넌트 : 독립적인 기능, 교체가능
  - 부모자식 관계
  - 형제관계 (데이터 다이렉트로 주고받지 않음, 부모 거쳐서)
  - 조상-후손 관꼐
  - 지역 등록 : 부모 컴포넌트가 자식 컴포넌트를 임포트하여 사용, 템플릿에서 내장 태그처럼 사용 가능
  - 전역 등록
  - 컴포넌트 라이프사이클 : 생성, 부착(마운팅)-화면요소에 직접 접근할 수 있게 되며 백엔드 api를 호출하여 초기 데이터를 받아오기에 가장 완벽한 타이밍, 갱신, 소멸
  - 생성 전(setup()), 마운트 완료(onMounted(), 초기 DOM조작, api 호출), 업데이트 후(onUpdated(), 콘솔로그남길때?나 사용(이것도 watch사용하긴함)), 언마운트(onUnmounted(), 컴포넌트가 DOM제거된 후 호출, 메모리정리)

- Props
  - defineProps() - 속성 정의하기, 부모의 물려줄 데이터와 규격 지정
  - 부모는 자식 컴포넌트를 호출하면서 데이터를 넘겨줄수 있는 상태가 됨, 즉 반응형데이터로 연결 가능
  - readonly 부모에서 온 건 리드온리
  - Component의 Data는 camelCase로 Component의 속성은 kebab-case로 작성
  - validation 부모가 넘긴 데이터에 대한 유효성 검사, required, default, validator
  - 배열이랑 객체 자료형 default지정 시 화살표 함수형태로 넘겨야됨

- Emits
  - defineEmits(['이벤트타입']) 정의, emit('이벤트 타입', 보낼데이터)로 이벤트 발생
  - 부모는 @이벤트타입=함수 등으로 받고, 함수안에 파라미터에 보낸데이터를 받음
  - 이벤트명는 kebab

- provide/inject 개념(추천은 안함, 컴포넌트쓰는 의미가 희석)
  - props drilling 현상 : 아키텍처의 계층이 깊어질때, 중간 위치 컴포넌트들은 해당 데이터 쓰지도 않는데 토스하는 과정이 있어야함
  - 그러나 pinia로 인해 provide&inject사용 빈도는 높지 않다.(전체는 store사용)
  - 앱 전역 주입(app.provide)는 쓰임(주로 값만 집어넣을떄)

- component slot
  - 자식 컴포넌트의 특정 구역을 비워두고, 부모 템플릿 주입, slot태그 이용
  - default slot, named slot(여러개 구분), scoped slot(자식 컴포넌트에서 부모컴포넌트로 데이터 전달할 때 사용)

- vue Router
  - SPA 구조
  - 브라우저의 URL변화를 JavaScript엔진이 가로체서, 현재 주소(URL)에 매칭되는 미리 정의된 컴포넌트만 가상 DOM상에서 실시간에서 교체해주는 라이브러리
  - / , 즉 URL기반 관리
  - routes object : path, component(화살표 함수를 사용해서 import해도됨, 그러면 동적 로드)
  - 핵심 요소, route, router, RouterView, RouterLink
  - views 폴더 : route배열에서, RouterView 영억에 직접 렌더링 되는 컴포넌트들에 드감
  - useRoute() : 현재 활성화된 라우트 정보에 접근하기 위한 composable함수
    - 현재 활성화된 Route의 정보를 읽기 위한 Composition API 함수
    - path, params, query, name 등의 정보에 접근 가능
    - 반환되는 route 객체는 반응형이므로 URL이 변경되면 관련 값도 자동 갱신
    - Template, computed, watch 등에서 활용 가능
    - 주소창 뒤에 콜론(:) 식별자를 붙여 변수화(/weather/:cityId)하며 이 부분을 동적 세그먼트(Dynamic Segment)라 한다
  - useRouter() : 사용자가 클릭하는게 아니라 자바스크립트코드로 페이지를 이동할때 = programmatic Navigation 해야할때 불러오는 객체
    - .push()(히스토리 항목 추가하면서 즉 뒤로가기 가능), .replace()(뒤로가기 불가), router.go(n)(히스토리 스택에서 n단계만큼 앞/뒤로 이동)
  - navigation guard 특정 라우트로 진입하기 직전, 중간에 가로채서 접근권한 검사 및 페이지 리다이렋ㄴ 같은 사용자 정의 로직을 실행할수 있게함(global guard)
    - router.beforeEach 새로운 라우트로의 이동이 시작되기 직전 트리거
  - route가 컴포넌트가 없으면? 빈화면 (보통 개발 중간에 발생함), 개발중 페이집니다 띄어주고 고객한테 알려주기.
  - catch-all Route 상단 라우트와 매칭되지 않는 모든 경로를 notFoundView로 리다이렉트(맨 마지막에 두기)
- Pinia Basic(Store)
  - 인증스토어(authStore.js), UI스토어(uiStore.js), 알림스토어(alertStore.js), 공통코드스토어 (commonStore.js)
  - state(반응형 데이터 변수, 전역 공유), getters, actions
  - defineStore()로 생성, 변수의 식별자는 use+파일명+Store 규칙, 앵간하면 actions를 써서 데이터 조작하기
  - store는 구조분해할당 시 반응형이 유실될수 있다. 쓰지 말기, 그냥 객체 받아서 사용
  - 왜 굳이 유저정보 세션에 놓지 않고 인증스토어를 따로 하나? , Component마다 서버에 사용자 정보를 반복 요청하지 않고 Store를 통해 빠르게 UI에 반영. 단, Store는 UI 상태 관리용이며 실제 접근 권한은 서버에서 Token 등을 검증하여 결정, JWT와 같은 인증은 서버가 인증 Session을 직접 보관할 필요가 적어 분산 시스템·MSA 환경에서 활용하기 용이함

# 궁금한점

- 배열이랑 객체 자료형 default지정 시 화살표 함수형태로 넘겨야됨 왜?
  - 핵심 이유는 객체와 배열은 참조형(reference type) 이기 때문
  - Object / Array는 참조형이므로 기본값을 함수로 반환해서 컴포넌트 인스턴스마다 새로운 객체·배열을 만들도록 한다
  - () => ({})에서 객체에 괄호를 씌우는 이유. () => {}라고 쓰면 {}를 함수 본문으로 해석하기 때문에, 객체를 바로 반환하려면 () => ({})라고 씀.
