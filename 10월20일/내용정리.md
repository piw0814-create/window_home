- 젠킨스의 핵심 파일
  - 1. Jenkinsfile → 전체 자동화 순서
  - 2. pom.xml → Java/Spring Boot 빌드 방법
  - 3. Dockerfile → 컨테이너 이미지 만드는 방법
  - 4. base/deployment.yaml → 애플리케이션 Pod 실행 방법
  - 5. base/service.yaml → Pod 접근 방법
  - 6. overlays/dev/kustomization.yaml → dev 환경에서 위 설정들을 어떻게 조합/변경할지
  - 그리고 이를 보조하는 게 patch-deployment.yaml, configmap.yaml, Jenkins Credentials, kubeconfig
  - 인증정보는 jenkins.yaml / kubeconfig, 실제 Kubernetes 권한은 Role / RoleBinding YAML, Docker 접근은 local-run.sh에서 준다.

- CI는 젠킨스, CD는 argoCD
- Jenkins는 “새 버전을 만들어내는 도구”, Argo CD는 “그 버전이 Git에 선언된 상태대로 Kubernetes에서 계속 유지되게 하는 도구”
- 젠킨스가 도커 이미지, 쿠버네티스 관련 변경사항까지 다시 깃에 올리고 즉 배포를 하기위한 정보를 깃에 올리고(브랜치 따로 나눠서), argoCD가 감지하고 실제 쿠버네티스랑 비교하며 맞춤
- Jenkins가 main에서 코드를 빌드하고, 결과 이미지 버전만 gitops 브랜치에 기록하면, Argo CD가 그 gitops 브랜치를 보고 배포한다. 브랜치를 나누는 핵심 이유는 CI와 CD 역할 분리 + Jenkins 자기 commit에 의한 재빌드 방지
- Jenkins는 GitHub 소스를 빌드해 이미지로 만들고 Harbor에 올린 뒤, 그 새 이미지 버전을 Kubernetes 배포 설정에 반영해서 gitops 브랜치에 올린다

1. Jenkins가 새 이미지 생성
   ↓
2. Harbor에 이미지 저장
   ↓
3. Kustomize의 newTag 변경
   ↓
4. "이제 이 이미지를 써라"라고 배포 설정 갱신
   ↓
5. Argo CD가 그 설정을 보고 실제 Kubernetes에 배포

- Jnkins는 Git의 “원하는 상태”를 갱신하고, Argo CD는 그 원하는 상태가 실제 클러스터에서도 유지되도록 보장한다.
- Git을 SSOT로 삼는 GitOps 원칙을 Kubernetes에서 지속적으로 실행해주는 도구가 Argo CD

- gitOps
  - git을 통해 코트돠 인프파를 함께 관리 하고, 선언적 형상 관리로 개발과 운영을 이음

- Argo CD
  - 쿠버네티니스 환경에서 gitops방식으로 애플리케이션 배포를 자동화하고 관리하는 도구
  - git의 desired state 와 실제 쿠버 클러스터의 상태를 지속적으로 비교하고 둘을 일치
  - 리소스에 대한걸 gitOps로 관리. 깃 기반으로 리소스 원상복구 가능.(리소스의 집합 = 애플리케이션)
  - Application = Git의 특정 배포 설정 경로와 실제 Kubernetes 배포 위치를 연결해주는 관리 단위

- custom resource : 쿠버네티스에서 기본제공하지않은 새로운 리소스 종류를 사용자가 직접 정의
  - kubectl로 생성/조회/삭제 할 수 있는 사용자 정의 객체
  - kind : database
    - engine, replicas
  - application, applicationSet, appProject
  - CRD는 Kubernetes에 새로운 리소스 종류를 추가하는 ‘설계도’이고, CR은 그 설계도로 만든 실제 객체. Argo CD의 Application도 CRD로 추가된 리소스라서, 웹 UI 대신 YAML로 선언해서 만들고 관리할 수 있음.

- 패키지 매니저 helm chart
  - Helm Chart = Kubernetes 애플리케이션의 Deployment, Service, ConfigMap 등을 변수화해서 하나의 설치 패키지처럼 만든 것.
  - Chart = Kubernetes 앱 패키지, 어떻게 Kubernetes YAML을 만들지( 이름, 버전, 설명, 의존성 같은 패키지 정보), values.yaml = 변경할 설정값(이미지 태그, replica 수, service port 같은 변경값), templates/ = YAML 틀(Deployment, Service, Ingress 등 K8s YAML 틀), Release = 실제 설치된 Chart 한 개.
- Kustomize = 우리 YAML을 환경별로 조금씩 수정
- Helm = 하나의 Kubernetes 앱을 재사용 가능한 설치 패키지로 만듦
