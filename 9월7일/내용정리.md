- ip + port (서비스/프로세스를 구분), DNS,
- 127.0.0.1 : localhost, 루프백 ip, 내부 통신용
- 포트는 유일해야됨
- 프로세스 : 실행중인 프로그램의 인스턴스, 긱 프로세스 간 독립적인 메모리(힙) 할당, 스케줄링, 메모리는 넘치면 죽음, cpu(스케줄링)은 느려지기만함
- 스레드 : 프로세스 내에서 실행되는 작업단위, 스택(일시 저장)을 가짐, 프로세스의 메모리 공간을 공유
- public, private IP
- Application layer 진입점, 소켓 : ip와 포트를 통해 통신하기 위한 추상화된 통신 엔드포인트, IP와 포트정보가 담김
- HTTP : 웹에서 데이터를 주고받기위한 통신규약
- Load(서버) balancer : 요청 트래픽을 여러 노드에 분배/분산
- router : 네트워크를 연결/확장, 인터넷 -> 라우터들의 집합(ip로 연결)
- gateway : 서비스/앱으로 진입점, 외부 ip를 내부 ip로 변환, 인증...해더변경
- yaml 포멧 : 키:값 쌍, 리스트 - 로 시작
- 비동기 : 요청, 처리, 응답 분리, 결과 도착 시 콜백 등으로 처리
- rest 설계 : 무상태성, 캐시가능
- 네트워크 참조 모델 : OSI 7 Layer
- 쉘(Shell): 사용자가 커널을 직접 다루지 않고 명령어로 시스템을 사용할 수 있게 해주는 인터페이스. 사용자의 명령을 해석해서 커널 쪽에 전달하고, 명령 실행에 따라 새로운 프로세스가 실행
- 커널(Kernel): CPU, 메모리, 디스크, 네트워크 같은 하드웨어 자원을 직접 제어·관리하는 OS의 핵심 프로그램. 응용 프로그램이 하드웨어를 사용할 수 있도록 Kernel API를 제공
- Linux는 Kernel이고, 우리가 실제로 쓰는 Ubuntu 같은 OS는 Linux Kernel + GNU 도구 + 패키지 관리자 + 기타 소프트웨어를 묶은 배포판
- 쉘 종류 : sh, bash, zsh
  - ~/.bashrc, .... : 쉘 초기화 스크립트
- 리눅스 파일관련 시스템
- 실행 퍼미션 처리
- pwd, cd, ls, cp, mv, find, rm, ...
- 가상화
  - 하이퍼바이저 : 물리 서버 자원을 여러 VM에 나눠주고, VM들을 생성·실행·관리하는 가상화 관리자
    - 타입1, 타입2(host OS)
  - VM 구조의 문제점
    - 물리 서버를 서비스화하여 동적 할당을 지원
    - but 애플리케이션의 설치 및 운영은 기존 전통적인 물리 서버 환경과 동일한 구조, vm하나하나 마다 다시 환경 만듬
    - 어플리케이션 영역에서 확장,탄력성 등이 부족
    - VM은 서버 자원 자체는 동적 할당 가능하지만, 애플리케이션 실행 환경까지 가볍고 일관되게 패키징하는 데 한계가 있음
- 컨테이너
  - 리눅스 커널 환경으로 OS환경 통합 -> 빠른 시작
  - 애플리케이션과 실행환경을 통합한 이미지로 생성 관리(배포단위에서 OS 이미지 제거)
  - 새 이미지는 기존 이미지의 공통 레이어를 재사용하고, 변경된 부분만 새로운 레이어로 쌓아 만든다.
  - docker exec 컨테이너 echo "~~", docker exec \_it hello /bin/bash
    - docker exec → 실행 중인 컨테이너 내부에서 명령 실행
  - 이미지는 리드온리 -> 컨테이너 실행(바꿔기 시작, 저장 안됨)
    - -> 계속 저장하기위함 -> 볼륨, 외부에 유지시켜줄수있는 볼륨
  - Dockerfile = 어떤 실행환경을 만들지 적는 설계도
  - docker build = 그 설계도를 읽어서 기존 Base Image의 레이어를 재사용하고, 필요한 변경사항을 새 레이어로 추가하여 새로운 Image를 만드는 과정
  - Image = 실행 가능한 환경이 준비된 Read-Only 패키지
  - docker run = 그 Image를 기반으로 실제 Container를 생성하고 프로그램을 실행
  - 멀티 스테이지 빌드(Multi-Stage Build) : 이미지를 만드는 데 필요한 환경과, 실제 실행할 때 필요한 환경을 분리
    - ex) Node 환경에서 Vue를 빌드한 뒤, 빌드 결과인 dist만 Nginx 기반의 새로운 배포 Stage로 복사하여 작고 안전한 최종 이미지를 만든다.
  - ARG는 Docker 이미지 빌드할 때만 쓰는 변수
    - 멀티 스테이지에서는 FROM마다 빌드 Stage의 범위가 구분되므로, 전역 ARG 값을 각 Stage 내부에서 사용하려면 그 Stage에서 다시 ARG를 선언한다.
  - LABEL : 이미지에 설명용 메타데이터를 붙이는 명령, 빌드나 컨테이너 실행 동작에는 영향을 주지 않음
  - CMD : 이 이미지로 컨테이너를 실행했을 때 기본적으로 어떤 명령을 실행할지 지정
    - Nginx를 foreground로 실행하는 이유 = Nginx를 컨테이너의 메인 프로세스로 유지해서 컨테이너가 계속 살아 있게 하고, 종료 신호도 제대로 받게 하기 위해서.
    - 컨테이너는 메인 프로세스(PID 1)가 종료되면 같이 종료되므로, nginx를 daemon(background)으로 보내지 않고 foreground로 실행한다.
  - EXPOSE : 컨테이너 내부 애플리케이션이 어떤 포트를 쓴다고 명시
  - copy : 로컬 파일 복사
  - WORKDIR: 작업 디렉토리 고정
  - user : Dockerfile 이후 명령과 컨테이너 프로세스를 실행할 사용자/그룹을 지정. 기본 root 실행을 피하고 최소 권한 원칙을 적용하기 위해 사용. 사용자 계정은 미리 생성
  - env: 환경변수, 스태이징
