- 모델 성능은 평준화되고 있고, 차이는 어떤 문제를 골랐는가, 오류-비용-책임을 어떻게 운영하는가
  - llm호출 코드보다 스키마,검증,로그,평가 코드가 더 길어진다

- 회원가입 비밀번호를 BCrypt 해시로 바꿈, db저장, 로그인할 때 입력한 비밀번호가 DB에 저장된 해시와 일치하는지 확인, 로그인 API에서 방금 완성한 비밀번호 검사 함수를 호출하도록 연결, 브라우저가 보낸 세션 ID로 로그인한 사용자를 찾는 부분, 브라우저가 보낸 JWT가 유효한지 검증, 세션과 JWT가 모두 유효하지 않을 때 접근을 거부하는 조건

- 회원가입: 비밀번호를 해시로 저장 -> 로그인: 사용자와 비밀번호를 확인. -> 로그인 성공: 세션과 JWT를 함께 발급. -> 인증 확인: 세션 또는 JWT가 유효한지 검사. -> 로그아웃: 세션과 브라우저 쿠키를 제거

- Java에서 로그인 → JWT 쿠키 발급 -> Voice AI에서 JWT 검증 -> 인증된 사용자에게 통번역 화면 제공 —> 녹음 WebM → WAV 변환 -> STT로 음성을 텍스트로 변환 —> 선택한 언어로 번역 —> 번역문을 MP3로 합성

- ⑤ 비밀번호 보안 — BCrypt 해싱 및 검증
  - ⑤-A. 회원가입 시 비밀번호 저장

    [정답]
    - BCrypt.hashpw(rawPassword, BCrypt.gensalt(12))

    [해설]
    - 사용자의 비밀번호를 평문으로 저장하지 않고, 무작위 salt가 포함된 BCrypt 해시로 변환하여 저장합니다.

    - BCrypt.gensalt(12)의 12는 해싱 비용 계수를 의미합니다.

  - ⑤-B. 로그인 시 비밀번호 검증

    [정답]
    - BCrypt.checkpw(rawPassword, u.getPassword())

    [해설]
    - 사용자가 입력한 비밀번호와 데이터베이스에 저장된 BCrypt 해시를 비교하여 일치 여부를 확인합니다.

    - 단순 문자열 비교나 평문 비밀번호 저장을 사용하지 않습니다.

- ① Java 인증 서버와 JWT 검증 연결

- 수정 파일: app/main.py

  [정답]
  - payload = jwt.decode(access_token, SECRET_KEY, algorithms=[ALGORITHM], issuer=ISSUER)

  [해설]
  - Java 인증 서버에서 발급한 JWT를 Python FastAPI 서버에서 검증하는 부분입니다.

  - JWT는 단순히 내용을 디코딩하는 것만으로 신뢰할 수 없습니다.

  - jwt.decode()를 통해 다음 항목을 검증합니다.
    - 서명(Signature): 토큰이 변조되지 않았는지 확인
    - 알고리즘(Algorithm): 허용된 서명 알고리즘인지 확인
    - 발급자(Issuer): 신뢰할 수 있는 서버에서 발급했는지 확인
    - 만료 시간(Expiration): 토큰의 유효기간이 지나지 않았는지 확인

  - Java 인증 서버와 Python 서버의 JWT 설정이 일치해야 정상적으로 인증됩니다.

- ① PDF 청크 설계 — 텍스트 분할 및 중첩 설정

  [정답]
  - splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)

  [해설]
  - PDF에서 추출한 전체 텍스트를 검색 가능한 작은 단위(Chunk)로 나누는 부분입니다.

  - RAG에서는 문서 전체를 한 번에 임베딩하기보다 적절한 크기로 분할하여 벡터화합니다.
    - chunk_size=1000: 청크의 최대 크기를 1000자로 설정
    - chunk_overlap=100: 인접한 청크 사이에 최대 100자 정도의 중첩을 설정

  - 청크가 너무 크면 관련 없는 정보가 함께 포함될 수 있고, 중첩이 없으면 청크 경계에서 중요한 문맥이 끊어질 수 있습니다.

  - 따라서 적절한 청크 크기와 중첩을 설정하는 것이 검색 품질에 영향을 줍니다.

- ④ 유사 문서 검색 — 질문과 관련된 문서 추출

    - similarity_search_with_score(): 유사 문서와 거리 점수를 함께 반환

  - [처리 흐름]

  - 사용자 질문 입력 → 질문 임베딩 → 벡터 저장소에서 유사도 검색 → 상위 top_k개 문서 추출 → 문서와 거리 점수 반환

  - RAG는 전체 PDF를 LLM에 전달하는 대신, 질문과 관련성이 높은 문서 조각을 먼저 검색합니다.

  - 검색 결과의 거리 점수는 검색 품질을 점검하는 데 활용할 수 있습니다.

  - ※ FAISS의 기본 L2 거리 기준에서는 일반적으로 점수가 작을수록 벡터 간 거리가 가깝습니다.

━━━━━━━━━━━━━━━━━━━━

- ⑤ 검색 근거 기반 답변 생성 — LLM 호출

  [정답]
  - raw = llm.invoke([HumanMessage(content=full_prompt)]).content

  [해설]
  - 검색된 PDF 내용을 포함한 프롬프트를 LLM에 전달하여 답변을 생성하는 부분입니다.
    - full_prompt: 검색된 PDF 내용과 사용자 질문을 결합한 프롬프트
    - HumanMessage(): LLM에 전달할 사용자 메시지 구성
    - llm.invoke(): LLM 호출 및 응답 생성
    - .content: 생성된 응답에서 텍스트 내용 추출

  - [처리 흐름]

  - 사용자 질문 → FAISS 유사 문서 검색 → 검색된 문서 내용 추출 → 질문과 검색 근거를 결합 → full_prompt 생성 → LLM 호출 → 답변 반환

  - LLM은 FAISS 벡터 저장소를 직접 조회하지 않습니다.

  - 애플리케이션이 검색한 문서 내용을 프롬프트에 포함하여 전달해야 LLM이 해당 자료를 근거로 답변할 수 있습니다.

  - 이 과정이 RAG의 핵심인 검색 증강 생성(Retrieval-Augmented Generation)입니다.

━━━━━━━━━━━━━━━━━━━━

- 핵심 정리
  - ① PDF 청크 분할: 긴 문서를 검색 가능한 작은 단위로 분할

  - ② 임베딩 및 FAISS: 문서 청크를 벡터화하여 검색 저장소 생성

  - ③ 검색 출처 선택: web/pdf 요청에 따라 적절한 벡터 저장소 연결

  - ④ 유사 문서 검색: 사용자 질문과 의미적으로 가까운 문서 추출

  - ⑤ LLM 답변 생성: 검색된 문서를 근거로 답변 생성

  - 전체 RAG 처리 흐름

  - PDF 업로드 → 텍스트 추출 → 청크 분할 → OpenAI 임베딩 → FAISS 벡터 저장소 생성 → 사용자 질문 입력 → 검색 출처 선택 → 유사 문서 검색 → 검색 결과를 프롬프트에 결합 → LLM 답변 생성 → 사용자에게 결과 반환
