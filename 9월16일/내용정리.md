- concept drift : 특성-타깃 관계 자체가 바뀌는 현상, 일시적 노이즈인지 관계변화인지 구분하고, 최신 데이터로 재학습
  - data drift
  - PSI : 분포차이를 하나의 숫자로 정량화하는 드리프트 지표
- 서비스 운영 지표 : latency, Error Rate, Availability
  - 4xx/5xx : 클라이언트 측 입력오류/ 서버측 오류

  - 처리량(throughput) : 얼마나 많이 동시에 처리할 수 있나, 단위 시간당 성공적으로 처리한 요청 수 를 측정
- 정확도(Accuracy), recall(실제로 많이 잡았나), precision(오탐 했나), F1 score
- 가중 정확도 : 희귀 클래스 오분류를 드러내는 수정된 정확도, 희귀도 비례 가중치, 장애사항같이 적은 빈도의 클래스가 중요할때, 클래스별 정확도를 동등한 비중으로 평균

- pipeline stage : 파이프라인 그래프의 노드가 되는 작업 단위, t1 >> t2 ....처럼 의존성 명시

# 궁금한점

- 배치, 처리량, 레이턴시 관계

작은 batch
→ 요청을 바로 처리
→ latency 낮음
→ throughput은 낮을 수 있음

큰 batch
→ 여러 요청을 한꺼번에 처리
→ GPU 활용률 ↑
→ throughput ↑
→ 기다리는 시간 때문에 latency ↑ 가능

dynamic batching도 많이 생각

배치는 한 번의 추론에 묶어서 처리할 요청 수이고, 처리량은 단위 시간당 처리할 수 있는 요청 수다. 배치를 키우면 일반적으로 처리량은 좋아질 수 있지만 latency와 메모리 사용량이 증가하므로, 서비스의 응답시간 목표를 만족하는 범위에서 적절한 batch size를 찾는다.

1 worker vs 4 workers가 프로세스 수를 늘려 처리량을 높이는 방식이었다면, batching은 한 프로세스/모델이 한 번에 처리하는 샘플 수를 늘려 처리량을 높이는 방식

- 모델 파이프라인 기준으로 인원을 나눠서 작업을 한다던데 먼저 데이터 처리가 잘되고 차원수가 잘 정리되어야 학습도 짤수 있는거 아님?

데이터가 최종 완성되기 전에도 모델 담당자가 일을 시작할 수는 있지만, 최소한 입력 데이터의 규격은 먼저 합의되어야 한다. 실제 최종 학습과 성능 튜닝은 정제·특성 추출이 안정된 뒤에 제대로 진행된다.

- Scheduler, Executor, Worker
  - Scheduler가 “언제 실행할지” 결정하고, Executor가 “어떤 방식/어디서 실행할지” 정하며, Worker가 “실제로 Task를 실행한다.

- Airflow = DAG들을 관리하고 실행하는 시스템
- DAG = 하나의 워크플로 설계도, Airflow의 Scheduler/Executor가 실제 실행
- Task = DAG 안에서 실제로 실행되는 개별 작업

- @task는 일반 Python 함수를 Airflow가 스케줄링·의존성·상태·로그·재시도 등을 관리할 수 있는 Task 형태로 감싸주는 데코레이터, 오퍼레이터 역할
- KServe는 Kubernetes 위에서 모델 파일 위치와 모델 형식만 선언하면, 모델 다운로드 → 서버 실행 → Service 생성 → 추론 API 제공까지 표준화해주는 모델 서빙 플랫폼
- Spring Boot와 KServe를 Kubernetes 안에서 각자 별도 서비스로 띄우고 HTTP/gRPC로 연결
- vLLM은 Qwen 같은 LLM을 메모리에 올리고, 효율적으로 추론해서, OpenAI 호환 HTTP API로 서비스해주는 LLM 전용 서빙 엔진
