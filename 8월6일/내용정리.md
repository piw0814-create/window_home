전통적 개발은 현재 시점에서 미래의 완성품을 최대한 예측하고 계획하는 접근이고, 애자일은 불확실성을 인정하고 현재 만들 수 있는 작은 산출물에서 얻은 피드백으로 다음 산출물을 계속 결정하는 접근이다. 그래서 결과를 사전에 완전히 예측하기 어려운 AI 소프트웨어와 특히 잘 맞는다.

에자일 방법론
불확실성이 높고 변경이 많을수록 → 애자일에 유리
요구사항·설계가 명확하고 변경 비용이 클수록 → 계획 중심 방식에 유리
건물 설계, 금융 핵심 시스템, 하드웨어 연동처럼 중간에 설계를 바꾸는 비용이 매우 큰 프로젝트라면 처음부터 치밀하게 설계하는 게 중요

반대로 애자일은, 처음부터 정답을 모르는 경우(데이터가 분리가 잘되는 상황)
대략적인 방향 → 작은 기능 구현 → 사용자 확인 → 수정 → 다음 기능 → 다시 확인

# 궁금한점

지금 코드는 다른 환경변수간 데이터베이스 공유는 안되는 형식이 맞나?

    현재처럼 각 환경에서 MariaDB 컨테이너를 따로 실행하면 환경별 DB 데이터는 서로 공유되지 않는다.
    DB 이름·아이디·비밀번호가 같아도 DB 서버가 다르면 데이터는 별개다.
    여러 환경에서 같은 데이터를 쓰려면 동일한 원격 DB 서버를 바라보도록 설정해야 한다

도커가 굉장히 많다 이거 서비스별로 포트번호 각각 다 다르게 해야되고 이전에 같은 포트로 돌아가고 있는게 있으면 종료해야하나?

    MSA에서는 서비스마다 컨테이너가 따로 존재한다.
    컨테이너 내부 포트는 서로 같아도 가능하지만, 같은 PC에 공개하는 Host Port는 중복될 수 없다.
    예를 들어 이미 8080이나 3379를 사용하는 컨테이너가 있다면 종료하거나 다른 Host Port로 변경해야 한다.

지금 딴거는 서비스별로 컨테이너 라는거 알겠는데 eurek 이랑 kafka 라는게 새로보인다 무슨 역할이나?

    Docker Compose: 여러 컨테이너의 실행, 네트워크, 포트, 환경변수 등을 한 번에 구성하고 연결한다.
    Eureka: 서비스 등록소. 각 서비스가 어디에서 실행 중인지 등록하고 다른 서비스가 위치를 찾을 수 있게 한다.
    Kafka: 서비스 사이에서 이벤트를 전달하는 메시징 시스템이다.

    서비스 호출은 A가 B를 직접 찾아가서 “이 작업을 해줘”라고 요청하는 방식이고, 이벤트 통신은 A가 Kafka에 “이 일이 발생했다”고 알리면 그 이벤트를 구독한 B·C 등이 각자 필요한 작업을 수행하는 방식

어제 민감한 정보를 숨기는 .env파일로 도커를 실행해봤다. 근데 배포를 할때 다른 환경에서도 돌아갈려면 결국 거기서도 .env알아야 되지않나?
env는 보통 본인환경 껄로 설정하는 것들인가?

    .env는 DB 비밀번호, API Key 등 설정값과 민감정보를 코드에서 분리하기 위한 파일이다.
    배포 환경에서도 필요한 환경변수 값은 있어야 하지만, 개발자의 .env 파일을 그대로 전달하는 것은 아니다.
    개발·테스트·운영 환경이 각각 자기 환경에 맞는 값을 따로 설정하는 것이 일반적이다.
    즉 .env 형식은 공유할 수 있지만 실제 비밀값은 환경마다 별도로 관리한다.

rest api

    REST API는 클라이언트와 서버를 연결하는 기술이라기보다, HTTP 기반으로 "요청하는 프로그램"과 "응답하는 프로그램"을 연결하는 방식이다. 따라서 MSA에서는 한 서버가 다른 서버의 클라이언트가 되어 컨테이너 간에도 REST API를 사용할 수 있다.
