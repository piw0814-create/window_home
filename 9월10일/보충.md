- 서버 과부화
  - 서버 성능 높이기(scale up) : 비쌈, 서버한대에 모든 요청이 몰림(서버한개 죽으면 서비스 전체가 죽음), 동적이지 못함(자원낭비)
  - 여러 대 서버(scale out/scale in)
    - 서버 = 컴퓨터, 컨테이너 = 서비스를 실행하는 격리된 실행 단위
    - 사용자 수에 따라 서버 늘리고 줄임
    - but 서로 다른 서버가 같은 정보를 기억하고 있나?
      - 정보 공유할 수 있는 공간이 필요
        - stateless : 서버가 정보를 자기 내부에 저장 안하고 공용db에 저장
        - statefull
        - 실시간성이 필요한 경우, 동시 접속할 경우 statefull서버를 쓰는 경우 있지만, 보통 stateless
      - 요청은 어디로 보내지
        - load balancing : 들어오는 요청을 여러 서버에 나누어 보내는 것
- 쿠버네티스
  - 요청은 어떻게 나누지? 백엔드 컨테이너가 죽으면 누가 발견하고 조치하지?, 새 백엔드 컨테이너를 만든다면 어느 서버에 실행하지?, 서버 자체가 죽으면?
  - 배치, 개수유지, 복구, 확장, 연결 관리 -> 자동화
  - 대표 기능
    - 수평 확장 : 트래픽에 따라 같은 역할을 하는 컨테이너를 늘림
    - 로드밸런싱 : 살아있는 컨테이너 파악, 새로생기면 분배대상에 추가, 죽으면 분배대상에서 제외
    - 롤아웃, 롤백 자동화: 사용자가 쓰는 중에 버전업뎃 배포하고 싶을 떄, 컨테이별 순차 적용(롤아웃), 순차 롤백
    - 복구 자동화 : 컨테이너에 문제가 생기면 쿠버네티스가 이를 감지하고 자동으로 다시 실행하거나 교체
    - 빈 패킹 자동화 : 서버에다 적절하게 컨테이너를 배포, 노드 최소화
  - 클러스터 : 쿠버네티스가 관리한 전체 환경
    - 노드 : 서버, 컴퓨터
      - pod : 컨테이너를 실행하는 기본 단위, 특별한 경우 제외하고는 한 pod당 컨테이너 한개
  - 선언형 : 원하는 상태를 명시 -> 쿠버네티스에 전달 -> 리소스 반영
  - 원하는 상태는 manifest에 작성
    - kind : 어떤 리소스
    - spec : 어떤 상태를 원하나
      - replicas : 유지할 pod
      - image
  - 리소스 ; 쿠버네트스가 관리하는 대상, 리소스.yaml에 설정해서 제공
    - Deployment : 원하는 실행환경을 유지
    - service : pod는 계속 바뀌는데 어떻게 접근할까 -> pod들에 접근할 수 있는 service를 둠
- 쿠버네티스 컴포넌트
  - API Server : 관리 요청을 받는 곳
  - etcd : 클러스터 상태를 어디에 저장
  - controller manager : 원하는 상태와 현재 상태가 다를때
  - Scheduler : 새 pod를 어느 Node 배치하는지
  - kubelet : 해당 노드에서 누가 pod를 관리하는지
  - container runtime
- 상태가 중요한 워크로드 관리를 할려면 statefulset사용(db같은 경우)
- persistent storage : pod가 사라져도 데이터는 남는다
- 관리할때와 이용할때 요청흐름은 다름
- 우리가 할꺼
  - 어플리케이션 코드 작성
  - 컨테이너 이미지 생성
  - registry에 이미지 저장
  - 원하는 상태를 manifest에 선언
  - kuberctl.apply
