        +
        검색된 문서의 content
        → Prompt에 추가
        → LLM

        4. Advisor가 이 과정을 파이프라인화
        검색 → Prompt 보강 → LLM 호출
        → RAG

- Tool Calling : 도구설정, 메서드를 툴로 만듬
  - LLM : 특정 작업을 수행하기 위해 도구 호출을 요청하고 필요한 매개변수만 애플리케이션(spring AI)에게 전달
  - 애플리케이션(스프링ai) : 도구를 정의하고, 도구목록을 LLM에게 전달, 도구호출 요청을 처리하는데 유용한API, 인터페이스, 어노테이션 제공, llm이 도구 호출을 요청하면 해당 요청을 메소드로 매핑한뒤 결과를 다시 llm에 전달하는 흐름도 자동 처리
  - @Tool : 이 메소드는 어떤 기능을 제공하는지 설명, 이 정보는 LLM에 ToolDefinition으로 Prompt에 함께 전달
    - name
    - description
    - @ToolParam : 입력으로 넣는 파라메터에 대한 설명
- MCP : LLM이 외부 Tool들을 표준 방식으로 찾아서 쓰게 해주는 통신 규격
  - tool list, tool call, JSON-RPC기반, 표준 메시지 구조
  - Tool Calling은 “도구를 쓰는 기능”, MCP는 “그 도구들을 여러 앱과 서버에서 공통 규격으로 연결하기 위한 표준
  - ① MCP 서버의 tools/list 엔드포인트를 호출해 사용 가능한 툴 목록 검색 (ToolCallbackProvider)
  - ② 사용자가 MCP 호스트에게 요청 Prompt를 전달
  - ③ 사용자의 Prompt + 사전에 받아온 Tool List를 LLM에 전달, LLM은 Tool List 중 사용 Tool 들을 선택해서 응답
  - ④ MCP Client를 통해 MCP Server에게 tools/call 엔드포인트로 해당 툴 사용을 요청
  - ⑤ MCP Server의 Tool 응답 + 기존 사용자의 Prompt를 다시 LLM로 전달하고, LLM은 이를 기반으로 최종 응답을 생성
  - 통신 방식
    - stdio, Stateful Streamable HTTP , Stateless Streamable HTTP
- 에이전트 : LLM + Memory + RAG + Tool을 하나의 목적을 위해 묶어서, LLM이 다음 행동을 스스로 결정하게 만든 구조
  - ① 역할을 정하는 System Prompt, ② 역할에 필요한 Tool들, ③ 상태를 유지하며 LLM을 호출하는 ChatClient의 조합
  - 멀티 에이전트 : 역할이 다른 여러 Agent를 두고, 상위 Orchestrator가 사용자 요청을 쪼개서 적절한 Agent에게 위임하는 구조
